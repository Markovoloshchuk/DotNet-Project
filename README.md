# Lab 01: Проектування баз даних для мікросервісної архітектури

## 1. Опис предметної області
Предметна область: **Система управління медичною клінікою («Арніка»)**. 
Система призначена для автоматизації роботи медичного закладу: обліку пацієнтів, планування прийомів лікарів, ведення каталогу медичних послуг та збору відгуків і консультаційних обговорень.

Архітектура побудована за принципами мікросервісного підходу (Domain-Driven Design, Bounded Contexts). Між мікросервісними базами даних **відсутні прямі зовнішні ключі (FOREIGN KEY)** та спільні таблиці[cite: 2, 7].

---

## 2. Межі контекстів (Bounded Contexts)

1. **Сервіс «Записи та візити» (Appointments / Проєкт №1):**
   - **Тип БД:** SQL Server (ADO.NET & Dapper)[cite: 1, 2].
   - **Призначення:** Управління транзакційними процесами запису пацієнтів на прийом до лікарів, зміною статусів візитів, веденням розкладу та рецептів.
   - **Основні сутності:** `Patients`, `Doctors`, `Appointments`, `Prescriptions`, `AppointmentServices`.

2. **Сервіс «Каталог послуг» (Catalog / Проєкт №2):**
   - **Тип БД:** SQL Server (EF Core Code First)[cite: 1, 2].
   - **Призначення:** Зберігання структурованого каталогу медичних послуг, категорій, медичного обладнання та комплексних пакетів послуг.
   - **Основні сутності:** `ServiceCategories`, `MedicalServices`, `Equipment`, `ServicePackages`, `PackageServices`.

3. **Сервіс «Відгуки та обговорення» (Feedback / Проєкт №3):**
   - **Тип БД:** MongoDB[cite: 1, 2].
   - **Призначення:** Зберігання динамічних відгуків пацієнтів, рейтингів лікарів, вкладених коментарів до обговорень діагнозів та консультаційних заміток.
   - **Основні колекції:** `PatientReviews`, `DoctorDiscussions`, `ConsultationNotes`.

## 3. Політика дублювання даних та узгодженості
Оскільки кожен мікросервіс володіє власною базою даних, для забезпечення автономії та оптимізації читання застосовується контрольоване дублювання даних[cite: 2]:

| Дані, що дублюються | Де зберігаються (Джерело) | Куди дублюються (Копія) | Механізм синхронізації / узгодженості |
|---------------------|--------------------------|-------------------------|----------------------------------------|
| `DoctorName`, `Specialization` | Сервіс «Каталог» / `Doctors` | Сервіс «Записи» / `Appointments` | Події інтеграції (Event Bus / RabbitMQ) при зміні профілю лікаря (Eventual Consistency)[cite: 2]. |
| `ServiceName`, `Price` | Сервіс «Каталог» / `MedicalServices` | Сервіс «Записи» / `AppointmentServices` | Кешування ціни та назви на момент створення замовлення для фіксації фінансової історії. |
