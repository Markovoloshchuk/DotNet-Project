# Практичне заняття №01. Проєктування баз даних для мікросервісної архітектури

## 1. Опис предметної області

Предметна область: **система управління медичною клінікою «Арніка»**.

Система призначена для автоматизації роботи медичного закладу: обліку пацієнтів, планування прийомів лікарів, ведення каталогу медичних послуг, зберігання відгуків і консультаційних обговорень.

Архітектура побудована за принципами мікросервісного підходу, Domain-Driven Design (DDD) та Bounded Contexts. Кожен сервіс володіє власною базою даних. Між базами даних різних сервісів відсутні прямі зовнішні ключі (FOREIGN KEY) та спільні таблиці.

## 2. Межі контекстів (Bounded Contexts)

1. **Сервіс «Записи та візити» (Appointments / Проєкт №1):**
   - Тип БД: SQL Server.
   - Технології доступу до даних: ADO.NET та Dapper.
   - Призначення: управління записами пацієнтів на прийом до лікарів, зміною статусів візитів, розкладом і рецептами.
   - Основні сутності: `Patients`, `Doctors`, `Appointments`, `Prescriptions`, `AppointmentServices`.

2. **Сервіс «Каталог послуг» (Catalog / Проєкт №2):**
   - Тип БД: SQL Server.
   - Підхід до роботи з даними: Entity Framework Core Code First.
   - Призначення: зберігання каталогу медичних послуг, категорій, медичного обладнання та комплексних пакетів послуг.
   - Основні сутності: `ServiceCategories`, `MedicalServices`, `Equipment`, `ServicePackages`, `PackageServices`.

3. **Сервіс «Відгуки та обговорення» (Feedback / Проєкт №3):**
   - Тип БД: MongoDB.
   - Призначення: зберігання відгуків пацієнтів, рейтингів лікарів, коментарів до обговорень діагнозів та консультаційних нотаток.
   - Основні колекції: `PatientReviews`, `DoctorDiscussions`, `ConsultationNotes`.

## 3. Політика дублювання даних та узгодженості

Оскільки кожен мікросервіс володіє власною базою даних, для забезпечення автономності та оптимізації читання застосовується контрольоване дублювання даних.

| Дані, що дублюються | Джерело | Копія | Механізм узгодженості |
|---|---|---|---|
| `DoctorName`, `Specialization` | Сервіс Catalog | Сервіс Appointments | Події інтеграції через Event Bus / RabbitMQ, eventual consistency |
| `ServiceName`, `Price` | Сервіс Catalog | `AppointmentServices` у Appointments | Збереження назви та ціни послуги на момент створення запису |

# Практичне заняття №02. Розробка WEB-додатків на платформі .NET

## 4. Мета роботи

Розробити WEB API для сервісу записів на прийом до лікарів (Appointments) із використанням платформи ASP.NET Core та реалізувати тришарову архітектуру:

- **DAL (Data Access Layer)** — рівень доступу до даних.
- **BLL (Business Logic Layer)** — рівень бізнес-логіки.
- **API (Presentation Layer)** — рівень взаємодії з клієнтом.

Додатково реалізувати патерни Generic Repository та Unit of Work, використовувати ADO.NET і Dapper, DTO та AutoMapper, асинхронні HTTP-методи й керування залежностями через .NET Aspire.

## 6. Архітектура та реалізовані компоненти

### 6.1. Domain Layer

Проєкт `Appointments.Domain` містить доменні моделі:

- `Patient` — пацієнт;
- `Doctor` — лікар;
- `Appointment` — запис на прийом;
- `AppointmentService` — послуга, пов'язана із записом;
- `Prescription` — рецепт.

Також реалізовано константи статусів запису (`Scheduled`, `Completed`, `Cancelled`) та ієрархію доменних винятків для обробки помилок бізнес-логіки.

### 6.2. Data Access Layer (DAL)

Проєкт `Appointments.Dal` відповідає за взаємодію з SQL Server.

Реалізовані компоненти:

- `IGenericRepository<T>` — узагальнений інтерфейс CRUD-операцій;
- `BaseDapperRepository<T>` — базовий репозиторій із використанням Dapper;
- `PatientRepository` — репозиторій на основі чистого ADO.NET;
- `AppointmentRepository` — репозиторій записів із використанням Dapper;
- `AppointmentServiceRepository` — репозиторій послуг, пов'язаних із записами;
- `IUnitOfWork` та `UnitOfWork` — керування репозиторіями, спільним підключенням і транзакціями.

Для передачі значень у SQL-запити використовуються параметризовані команди. Транзакційні операції виконуються в межах одного підключення до бази даних.

### 6.3. Business Logic Layer (BLL)

Проєкт `Appointments.Bll` містить:

- DTO для створення, отримання та оновлення пацієнтів і записів;
- конфігурацію AutoMapper;
- інтерфейси бізнес-сервісів;
- реалізації `PatientService` та `AppointmentService`;
- валідацію вхідних даних;
- обробку доменних помилок.

Під час створення запису на прийом бізнес-операція охоплює створення запису та пов'язаних із ним послуг у межах однієї транзакції Unit of Work.

### 6.4. API Layer

Проєкт `Appointments.Api` реалізовано на ASP.NET Core Web API.

Основні компоненти:

- `PatientsController` — HTTP-операції з пацієнтами;
- `AppointmentsController` — HTTP-операції із записами на прийом;
- `DomainExceptionHandler` — централізована обробка доменних винятків;
- Swagger — документація та інтерактивний опис API.

Контролери використовують асинхронні методи та передають бізнес-операції до відповідних сервісів BLL.

Для помилок API використовується формат ProblemDetails.

## 7. HTTP API

Базовий маршрут для роботи з пацієнтами:

`/api/patients`

| HTTP-метод | Маршрут | Призначення |
|---|---|---|
| GET | `/api/patients` | Отримати список пацієнтів |
| GET | `/api/patients/{id}` | Отримати пацієнта за ідентифікатором |
| POST | `/api/patients` | Створити пацієнта |
| PUT | `/api/patients/{id}` | Оновити пацієнта |
| DELETE | `/api/patients/{id}` | Видалити пацієнта |

Базовий маршрут для роботи із записами:

`/api/appointments`

| HTTP-метод | Маршрут | Призначення |
|---|---|---|
| GET | `/api/appointments` | Отримати список записів |
| GET | `/api/appointments/{id}` | Отримати запис за ідентифікатором |
| POST | `/api/appointments` | Створити запис разом із послугами |
| PUT | `/api/appointments/{id}` | Оновити запис |
| DELETE | `/api/appointments/{id}` | Видалити запис |

### HTTP-статуси

API використовує стандартні HTTP-статуси:

- `200 OK` — успішне отримання або оновлення ресурсу;
- `201 Created` — успішне створення ресурсу;
- `204 No Content` — успішне видалення;
- `400 Bad Request` — помилка валідації;
- `404 Not Found` — ресурс не знайдено;
- `409 Conflict` — конфлікт бізнес-правил;
- `500 Internal Server Error` — внутрішня помилка сервера.

## 9. Порядок створення та налаштування бази даних

Для сервісу Appointments використовується база даних `ClinicAppointmentsDB`.

SQL Server або Azure SQL Edge повинен бути доступний на порту `1433`.

Для створення та початкового наповнення бази даних виконайте скрипти в такому порядку:

1. `db/p1/schema.sql` — створення таблиць і структури бази даних.
2. `db/p1/procedures.sql` — створення збережених процедур.
3. `db/p1/seed.sql` — початкове наповнення таблиць даними.

Скрипти можна виконувати через DBeaver або інший SQL-клієнт, сумісний із SQL Server.

Каталоги `db/p2/` та `db/p3/` призначені для скриптів інших предметних контекстів — Catalog і Feedback.

## 10. Налаштування підключення до бази даних

Рядок підключення для Appointments API передається через конфігурацію .NET Aspire.

Для збереження пароля використовується **User Secrets**, тому облікові дані не потрібно зберігати у відкритому вигляді в репозиторії.

З кореня репозиторію виконайте:

```bash
read -s -p "SQL Server sa password: " SA_PASSWORD
echo
dotnet user-secrets set "ConnectionStrings:AppointmentsDb" "Server=localhost,1433;Database=ClinicAppointmentsDB;User Id=sa;Password=${SA_PASSWORD};Encrypt=True;TrustServerCertificate=True;" --project Platform.AppHost
unset SA_PASSWORD
```

Введіть пароль користувача `sa`, який задано для SQL Server або Azure SQL Edge.

Після успішного виконання команда повідомить про збереження параметра `ConnectionStrings:AppointmentsDb` у сховищі секретів.

> Пароль не потрібно додавати до Git або передавати разом із вихідним кодом.

## 11. Збірка та запуск застосунку

### 11.1. Перевірка Docker-контейнера

Перевірте, чи працює контейнер SQL Server:

```bash
docker ps --filter name=sql-edge
```

Якщо контейнер зупинений, запустіть його:

```bash
docker start sql-edge
```

### 11.2. Збірка рішення

З кореневого каталогу репозиторію виконайте:

```bash
dotnet build Platform.slnx
```

Команда виконує відновлення залежностей і компіляцію всіх проєктів рішення.

### 11.3. Запуск через .NET Aspire

Запустіть AppHost:

```bash
dotnet run --project Platform.AppHost
```

Після запуску в терміналі відобразиться адреса Aspire Dashboard.

Відкрийте її в браузері. На вкладці **Resources** можна переглянути зареєстровані ресурси та стан API.

У `Platform.AppHost/AppHost.cs` використовується рядок підключення до наявної бази даних:

```csharp
var builder = DistributedApplication.CreateBuilder(args);

var appointmentsDb = builder.AddConnectionString("AppointmentsDb");

builder.AddProject<Projects.Appointments_Api>("appointments-api")
    .WithReference(appointmentsDb);

builder.Build().Run();
```

Aspire передає рядок підключення до API через конфігурацію середовища. Сам контейнер SQL Server запускається окремо та повинен бути активним до звернення API до бази даних.

### 11.4. Доступ до API та Swagger

Після запуску API доступні за адресами, які відображаються в Aspire Dashboard.

Для поточної конфігурації:

- HTTPS: `https://localhost:7141/`
- HTTP: `http://localhost:5130/`
- Swagger UI: `https://localhost:7141/swagger`

Порти можуть відрізнятися залежно від налаштувань запуску. Актуальні адреси потрібно дивитися в Aspire Dashboard.
